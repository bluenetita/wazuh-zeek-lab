# Wazuh

This directory contains the Wazuh configuration relevant to the cyber range: agents, decoders, custom rules, cross-source correlations, and RouterOS Active Response.

## Role

Wazuh receives both host-based telemetry and events generated by Zeek. In this lab it is used to:

- normalize events from different sources;
- correlate network and host telemetry;
- distinguish source/destination pairs in the SSH scenario;
- correlate reverse-shell activity with Auditd telemetry;
- build scanning and authentication chains;
- trigger RouterOS quarantine when it is explicitly enabled.

## Structure

| Directory | Contents |
|---|---|
| `manager/` | sanitized Manager `ossec.conf` |
| `agent-configs/` | configurations for ZeekVM, Client-Linux, and ServerDB |
| `decoders/` | Auditd/SSH/Zeek SSH decoders |
| `rules/` | Zeek, reverse-shell, scanning, and SSH rules |
| `active-response/` | RouterOS script and evidence collector |
| `integrations/`, `log-samples/`, `netplan/` | material already present in the repository |

## General flow

```text
Endpoint / Zeek
      |
  Wazuh Agent
      |
      v
 Wazuh Manager
      |
 Custom decoder
      |
   Ruleset
      |
 Alert / correlation
      |
 Active Response (only if enabled)
```

## Updated agent configurations

### ZeekVM

`agent-configs/zeek-agent-ossec.conf` collects standard Zeek logs and custom logs. For `ssh_bruteforce.log` it uses a dedicated prefix:

```text
zeek_ssh_json: <JSON>
```

This allows `010_zeek_ssh_pair_decoder.xml` to distinguish the custom SSH stream from other Zeek JSON data.

### ServerDB

`agent-configs/server-db-agent-ossec.conf` separates `sshd` from the rest of the journald messages and collects `/var/log/auth.log` with:

```xml
<out_format>$(log) wazuh_dst_ip=$(host_ip)</out_format>
```

The suffix makes the destination endpoint available to the SSH decoder. During the V1/V2 tests, the observed values were `10.3.30.3` and `10.3.30.4`, respectively.

### Client-Linux

`agent-configs/client-linux-agent-ossec.conf` retains collection of Auditd events used in reverse-shell correlations and enriches relevant events with the host IP address.

## Custom decoders

| File | Purpose |
|---|---|
| `000_audit_saddr_decoder.xml` | Extract relevant fields from Auditd `rs_connect` events |
| `010_zeek_ssh_pair_decoder.xml` | Parse Zeek SSH JSON and populate static `srcip`/`dstip` aliases |
| `0310-ssh_decoders.xml` | Customized SSH decoder exposing `src_ip`, `dest_ip`, `srcip`, and `dstip` |

The Manager excludes the corresponding stock SSH decoder to avoid duplicate definitions. Do not modify the Wazuh stock ruleset directly.

## Rules and correlations

### Zeek and scanning

`rules/002_zeek_rules_custom.xml` contains the custom Zeek rules, including scanning and SSH. `005_zeek_scanning_correlation.xml` handles scanning correlations in the multi-stage chain.

### Reverse shell + Auditd

`004_zeek_auditd_correlation.xml` links network signals with host-based events. IP semantics depend on the scenario: in an outbound reverse shell, the compromised host may be the connection source.

### SSH brute force

`9999_ssh_bruteforce_correlation.xml` uses the ordered source/destination pair. The main rules are:

| ID | Function |
|---|---|
| `100920` | SSH candidate from the Zeek sensor |
| `100921` | SSH success inferred by the Zeek path when available |
| `120935` | Zeek first, endpoint failures afterward |
| `120938` | valid-user endpoint failures first, Zeek afterward |
| `120939` | invalid-user endpoint failures first, Zeek afterward |
| `120936` | previous scanning + confirmed SSH brute force |
| `120937` | successful SSH authentication after the chain, same IP pair |
| `120940` | fan-out: same source, different victims |
| `120941` | fan-in: different sources, same victim |

Cross-agent correlations use `global_frequency` where required. Static `srcip`/`dstip` fields are used for pair comparisons.

## SSH validation

The real multi-host validation matrix includes:

| Case | Result |
|---|---|
| Confirmed A1->V1 | positive |
| A1->V1 antecedent + A1->V2 login | no `120937` |
| A1->V1 antecedent + A2->V1 login | no `120937` |
| A1->V1 + A1->V2 | `120940` |
| A1->V1 + A2->V1 | `120941` |
| A1->V1 + A2->V2 | two `120939` alerts, no false meta-alert |

See [`../../scenarios/ssh-bruteforce/TESTS.md`](../../scenarios/ssh-bruteforce/TESTS.md).

## RouterOS Active Response

`active-response/routeros_quarantine.py` receives a Wazuh alert, reads `data.src_ip`, and uses a dedicated SSH key to add the IP to the RouterOS `Quarantine` address list and remove matching active connections from connection tracking.

The private configuration is kept outside the repository. `routeros.conf.example` contains placeholders only.

**State of the included Manager export:** the command is defined, but the quarantine `<active-response>` block is commented out. Copying this configuration does not automatically enable containment.

The OFF/ON validation is documented in [`../../scenarios/active-response/README.md`](../../scenarios/active-response/README.md).

## Validation commands

Before applying changes on the Manager:

```bash
sudo /var/ossec/bin/wazuh-analysisd -t
```

To analyze an event in a test session:

```bash
sudo /var/ossec/bin/wazuh-logtest
```

A `wazuh-logtest` session does not replace end-to-end validation on the live Manager and does not automatically simulate separate Wazuh agents.

## Security

Do not version `client.keys`, `authd.pass`, private keys, live webhooks, RouterOS credentials, complete alert archives, or evidence-collector output containing sensitive information.
